Flow — Campus Assistant

Ask a general chatbot which UW instructor grades easiest and it will invent an answer. Flow looks it up.

Year 2026 Role Summer Research Intern, UW–Madison Summer AI Lab · team of 3 Stack Python · FastAPI · Postgres · Firestore
58tools, 11 packs
0vector databases
5,800+course listings
1,100+student orgs

The thesis

Flow is a UW–Madison assistant delivered as a web app and a CLI, both driven by one tool-calling LLM over a campus knowledge graph. It answers questions about student organizations, events, the course catalog with real historical grade distributions, dining menus, building hours, and live library and gym busyness.

The design commitment is narrow and load-bearing: the model narrates, it never decides. It chooses which tool to call; the tools read from a typed Postgres property graph, live HTTP feeds, and per-user Firestore documents. The answer is written from those results. When a lookup returns nothing the instruction is to say so rather than fill the gap.

There is no vector database anywhere in the system. Retrieval is exact SQL over a typed graph — which is why answers can cite real records.

That's an unfashionable choice and I think it's the right one for this problem. Campus data is structured: a course has a number, a dining hall has serving periods, a building has hours. Embedding all of that into a similarity search throws away the structure and buys fuzziness you then have to defend against. Nodes and typed edges — with twenty-five edge predicates, direct edges carrying full confidence and inferred ones carrying less — keep the structure and make the retrieval step auditable.

Keeping it current without lying about freshness

Campus data decays at wildly different rates. Grade history from past semesters is stable forever; how busy College Library is right now is stale in minutes. Treating those the same way is how an assistant ends up confidently wrong.

Ingestion is idempotent by construction — deterministic node IDs, conflict-tolerant loaders, and a savepoint per record so one malformed row can't take down a run. Re-running a crawl converges rather than duplicating. Canvas syncs never let an empty feed clobber a populated cache, because "the API returned nothing this minute" and "you have no assignments" are different facts.

The privacy path

My main piece of this was the degree-audit parser. A student uploads a DARS PDF; we extract completed courses, satisfied requirements, and what's still outstanding, deterministically — rules and regular expressions over pdfplumber, with no model in the extraction path — and then we throw the document away.

A staleness check nudges for a fresh upload after 180 days, because a degree audit from three semesters ago is a confidently wrong answer waiting to happen.

What I'd tell you in an interview

This is a team project — three of us — and it's deployed as a hardened service behind a TLS edge with scheduled data jobs and a golden-eval regression gate. It ran a live public demo with roughly a thousand logged chat turns across June and July. Things I would not claim:

  • General chat has no automated answer-verifier. Grounding there is architectural — tool-only data, pre-hedged tool summaries, an instruction never to fabricate — but no program diffs the model's prose against the retrieved evidence. Real verification exists only in the academic and planning cluster, where a formal validator re-derives constraints from scratch and distrusts the solver. I'd rather say that precisely than let "verification layer" do work it hasn't earned.
  • The newest academic features are flag-gated and off by default. The advisor harness, auto-planner, degree-wide requirements, and the DARS upload wizard are implemented and tested, but they are not the default experience.
  • There are no usage or accuracy metrics. The demo logs show it was used; they cannot separate students from our own testing, so "used" is as far as I'll take it.
  • It runs on a single uvicorn worker as a hard invariant. Fine at this scale; multi-worker would need shared state, and that's a real conversation rather than a footnote.
  • Building hours cover four pilot buildings, not campus.
