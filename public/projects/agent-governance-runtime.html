Agent Governance Runtime

A policy and audit layer for AI agents. It evaluates each tool call against deterministic policy before the call runs, and records the decision so it can be re-checked later without trusting the runtime that recorded it.

The problem

An agent that can call tools is an agent that can do damage. The common answer is a prompt asking it nicely. That isn't enforcement. It's a suggestion, evaluated by the same nondeterministic process you were trying to constrain.

So the decision about whether a call is permitted has to live outside the model, in code that is deterministic, separately testable, and auditable after the fact. The agent in this system holds no backend credentials at all; it asks the gateway, and the gateway decides. There is no secret-handling code in the repository because there are no secrets for the agent to hold. That absence is the design.

The harder half is the record. An audit log is only worth something if it still means something to someone who doesn't trust the process that produced it, including someone who has write access to the database.

Try it: forge a record and watch the chain break

Every decision is appended to a log where each record commits to the hash of the one before it: entry_hash = SHA-256(prev_hash + canonical(body)). The verifier below re-derives the whole chain from the log alone. It's the real algorithm running in your browser on real SHA-256. Not a video, not a mock.

What the verifier actually checks

Four checks, in a fixed order, returning the first broken sequence number and why:

  • Sequence equals index. Catches reordering and deletion from the middle, since a gap can't be papered over by renumbering.
  • Linkage. Each record's stored prev_hash equals the previous record's computed digest.
  • Hash-version monotonicity. A v1 record appearing after v2 began is invalid. Without this, an attacker downgrades a record to the older, narrower field projection and smuggles fields past the hash.
  • Hash equality. The body re-hashes to the stored digest.

That third check exists because the log survived a schema migration. Two field projections share one chain, 11 hashed fields in v1 and 26 in v2, so historical records stay byte-identical while newer ones seal fifteen more fields. Which projection applies is resolved from an explicit version field rather than inferred from which keys happen to be present; an unknown value throws rather than guessing. Database triggers RAISE(ABORT) on any write that would backfill a legacy row, because backfilling would invalidate every historical hash.

Canonical JSON isn't a formatting preference. If two identical records can serialize differently, the hash means nothing.

Keys sort at every level; arrays keep order; undefined, functions and symbols throw instead of being silently dropped; non-finite numbers are rejected; bigints serialize losslessly. There are three separate canonicalizers in the codebase. Audit, policy and authority each have their own, deliberately import-free, so the audit core's purity doesn't depend on the policy module staying pure. That's duplication I chose on purpose, and I expect to be asked about it.

Why the decision core has no imports

The part that decides is seven modules with an acyclic dependency graph. policy and authority are pure, importing nothing beyond themselves and node:crypto. audit imports both, because verification means replaying them.

Concurrency, and what a crash leaves behind

An append-only log is only append-only if concurrent writers can't interleave. Sequence allocation reads the tail inside a BEGIN IMMEDIATE transaction, so two writers cannot claim the same number. The wrapper is re-entrant: already inside a transaction, it just calls through, so nested calls join the outer commit instead of deadlocking.

Every state transition is a compare-and-swap: UPDATE … WHERE id = ? AND status = '<expected>' with a check that exactly one row changed. Double-dispatch isn't unlikely; it's unrepresentable.

The crash window has no clean solution

Between "approval committed" and "the backend actually did the thing," the process can die. Those two cannot be made atomic, because the backend call is precisely the part that might fail. So execution state is committed before dispatch, accepting an orphan-started window, and a boot-time pass fails any attempt the previous process abandoned.

Recovery terminally fails the abandoned attempt and returns the action to pending for a fresh human decision, while the old approval stays immutably consumed by the failed execution. The execution's approval id is unique, so a retry demands a new approval. The recovered action cannot reuse the original human's consent. A thirty-second grace period exists for exactly one reason: so a second process doesn't cancel a first process's live dispatch.

Failure is recorded in a separate transaction from the attempt. Success is one atomic commit; failure rolls that back and opens a new transaction to write the terminal state. The invariant is that a failure never erases the fact that something started.

The hardest problem

Proving that a recorded human approval actually authorized the side effect that occurred, across a process crash, a concurrent approver, and an adversary with write access to the database.

Sealing the action and its parameters is the easy half. The binding seals fourteen fields, and each one is there because omitting it opens a specific attack. Without the delegation id, an approval survives revocation of the authority it was granted under. Without the effective authority hash, the grant can be widened after the human looked at it. Without the action-event id, the approval detaches from the evaluation it was based on.

Checking it is roughly thirty comparisons and every one has to be the right comparison. The check re-canonicalizes the parameters, recomputes the payload hash, re-validates and re-hashes the authority snapshot, re-runs the historical policy engine and requires the result still be "approval required" with the same risk class and rule id, recomputes the authorization hash, re-resolves live provenance, and compares eighteen fields of the original evaluation event.

The subtle one is that the pending row's own timestamp is untrusted. Time-to-live is anchored to the hash-chained event, not the mutable row, so editing a created_at column cannot buy an attacker extra approval time.

The hard part isn't any single check. It's that the set has to be complete. Every unverified field is an attack.

And it has to be re-checkable offline by someone who doesn't trust the runtime. That verifier is the largest thing in the repository: it does zero I/O, re-derives policy and authority decisions rather than believing the stored ones, replays kill-switch state from the audit sequence and cross-checks it against what each evaluation recorded, detects cycles in two separate graphs, verifies both hash projections, and proves the approval-to-execution mapping is exactly one-to-one.

Re-deriving rather than trusting has a real cost, and it's worth naming: every historical policy version must be retained forever. An unknown version returns null rather than a decision, specifically so an unsupported version can never be mistaken for an authentic historical block.

What I'd tell you in an interview

The parts I'd want to be asked about, before you find them yourself:

  • There is no authentication. Identity comes from unverified headers and the code says so out loud. This project is about authorization, separation of duties and role gating, not about proving who you are.
  • There are no performance numbers because there are no benchmarks. I won't put a speed claim on work I didn't measure.
  • The verifier has a known hot spot, a filter over approvals and executions inside a loop over pending actions, which is O(n·m). It hasn't mattered at the scale this runs at, and I'd rather name it than have it found.
  • It's a single-machine SQLite runtime with no deployment, no telemetry, and no users. Multi-writer at real scale is a different problem than the one I solved.
  • The commit history understates it. Roughly five hours of commits; the largest artifacts (the verifier, the authority module, eight test files) landed in the working tree. Judge the code, not the graph.
